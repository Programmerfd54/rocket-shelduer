# Детальный анализ безопасности веб-приложения rocketchat-scheduler

## 1. Описание веб-приложения

### 1.1 Название и версия
- **Название:** rocketchat-scheduler (Планировщик сообщений Rocket.Chat)
- **Версия:** 0.1.0

### 1.2 Архитектура
- **Клиент-сервер:** SPA (Single Page Application) на React + серверный API на Next.js
- **Модель:** Next.js App Router (серверные компоненты + API Routes)
- **Связь:** REST API, аутентификация через JWT в httpOnly cookie

### 1.3 Используемые технологии
| Компонент | Технология |
|-----------|------------|
| Frontend | React 19, Next.js 16, Tailwind CSS, Radix UI |
| Backend | Next.js API Routes (Node.js) |
| База данных | PostgreSQL (Prisma ORM) |
| Аутентификация | JWT (jsonwebtoken/jose), bcrypt |
| Интеграция | Rocket.Chat REST API |
| Шифрование | AES-256-GCM (Node.js crypto) |

### 1.4 Основные функции и цели
- Планирование сообщений в каналы Rocket.Chat
- Управление пространствами (подключения к RC-серверам)
- Шаблоны сообщений (официальные и пользовательские)
- Администрирование пользователей, ролей, приглашений
- Справка и настройки пространств (скрытие системных сообщений, права RC)

## 2. Профиль пользователей

### 2.1 Типы пользователей
| Роль | Описание |
|------|----------|
| **ADMIN** | Суперадминистратор: все права, настройки, аудит, ограничения функций |
| **SUPPORT** | Поддержка: управление пользователями, назначение пространств, аудит |
| **ADM** | Администратор: доступ к назначенным пространствам, без админ-панели |
| **VOL** | Волонтёр: 1 пространство, ограниченный период доступа |
| **USER** | Обычный пользователь (по умолчанию) |

### 2.2 Права доступа
| Действие | ADMIN | SUPPORT | ADM | VOL | USER |
|----------|-------|---------|-----|-----|------|
| Админ-панель | ✓ | ✓ | ✓* | — | — |
| Управление пользователями | ✓ | ✓ | — | — | — |
| Назначение пространств | ✓ | ✓ | — | — | — |
| Архивирование пространств | ✓ | ✓ | ✓ | — | — |
| Добавление пространств | ✓ | ✓ | ✓ | ✓ | ✓ |
| Планирование сообщений | ✓ | ✓ | ✓ | ✓ | ✓ |
| Отправка «от имени» | ✓ | ✓ | ✓ | — | — |
| Шаблоны (официальные) | ✓ | ✓ | ✓ | — | — |

\* ADM видит админ-панель при наличии права, но без управления пользователями.

## 3. Методы тестирования

### 3.1 Перечень методов
- **Статический анализ кода (SAST):** поиск уязвимых паттернов, небезопасных функций
- **Динамический анализ (DAST):** сканирование работающего приложения
- **Тесты на проникновение:** ручная проверка OWASP Top 10
- **Анализ зависимостей:** npm audit, проверка уязвимостей в пакетах
- **Ревью конфигурации:** переменные окружения, заголовки, CORS, CSP

### 3.2 Инструменты
| Категория | Инструмент |
|-----------|------------|
| DAST | OWASP ZAP, Burp Suite |
| Сканирование зависимостей | npm audit, Snyk |
| Анализ трафика | Burp Suite Proxy |
| Fuzzing | ffuf, wfuzz (опционально) |

## 4. Типы уязвимостей

### 4.1 SQL-инъекции
- **Риск:** Низкий (Prisma ORM, параметризованные запросы)
- **Проверка:** Поиск raw SQL, невалидированный ввод в запросах

### 4.2 XSS (межсайтовый скриптинг)
- **Риск:** Средний (санитизация Help HTML через DOMPurify)
- **Проверка:** Ввод в поля сообщений, справки, отображение пользовательских данных

### 4.3 CSRF (межсайтовая подделка запросов)
- **Риск:** Низкий (SameSite cookie, проверка origin/referer)
- **Проверка:** Отсутствие CSRF-токенов, обход проверок origin

### 4.4 Аутентификация и сессии
- **Риск:** Средний
- **Проверка:** Слабые пароли, перебор, истечение сессий, перехват токенов, блокировка пользователей

### 4.5 Неправильная конфигурация
- **Риск:** Средний
- **Проверка:** Заголовки безопасности, CSP, CORS, раскрытие ошибок, дефолтные секреты

### 4.6 Дополнительно
- SSRF (валидация workspaceUrl)
- IDOR (проверка доступа к workspace/message по ID)
- Rate limiting (вход, API, invite token)
- Шифрование чувствительных данных (пароли пространств, auth tokens RC)

## 5. Ограничения и исключения

### 5.1 Разрешённые действия
- Тестирование на тестовой/разработческой среде
- Сканирование без нагрузки (rate limit)
- Ручные проверки с согласованными учётными записями

### 5.2 Запрещённые действия
- DoS/DDoS, нагрузочное тестирование без согласования
- Доступ к production-данным реальных пользователей
- Изменение данных без восстановления
- Тестирование на production без письменного разрешения

### 5.3 Чувствительная информация
- Пароли, JWT_SECRET, ENCRYPTION_KEY, CRON_SECRET
- Токены Rocket.Chat (authToken)
- Персональные данные пользователей (email, имена)

### 5.4 Условия отмены тестирования
- Обнаружение критической уязвимости, требующей немедленного исправления
- Несанкционированный доступ к данным
- Согласованные ограничения по времени/объёму

## Приложение: Известная проблема (set-default 400)

**Симптом:** `POST /api/workspace/{id}/space-settings/channels/set-default` возвращает 400 при наличии канала.

**Возможные причины:**
1. **Закрытый канал (type=p):** Rocket.Chat не поддерживает `groups.setDefault` — только `channels.setDefault` для публичных каналов. Кнопка «По умолчанию» отключена для закрытых каналов.
2. **Права RC:** у подключённого пользователя нет `edit-room` в Rocket.Chat
3. **Тип комнаты:** канал может быть в команде (team) — API может вести себя иначе
4. **Ошибка RC:** ответ Rocket.Chat содержит детали в `error`/`message`

**Рекомендация:** Проверить логи сервера (`[set-default] RC API error:`) и текст ошибки в toast на клиенте — он передаётся из ответа API.
