# Защита учётных данных Rocket.Chat

Кратко и честно: что хранится, как защищено и что остаётся риском.

## Что где хранится

| Данные | Где | Как |
|---|---|---|
| Пароль пользователя планировщика | `User.password` | bcrypt, cost 12 (необратимо; только проверка) |
| Токены приглашений / сброса пароля | `InviteToken.token`, `PasswordResetToken.token` | sha256 (сырой токен показывается один раз) |
| Сессия планировщика | cookie `__Host-auth-token` (JWT HS256, `JWT_SECRET`) + `Session` в БД | в БД — только id сессии и хеши отпечатка/устройства |
| Токен сессии Rocket.Chat | `WorkspaceConnection.authToken` | AES-256-GCM v2 (обратимо) |
| Пароль Rocket.Chat (вход «логин/пароль») | `WorkspaceConnection.encryptedPassword` | AES-256-GCM v2 (обратимо); `''` — пароль не хранится (вход по личному токену) |
| RC User ID | `WorkspaceConnection.userId_RC` | открыто (публичный идентификатор RC, сам по себе доступа не даёт) |
| Пароли LDAP bind / SMTP | `WorkspaceSettings.ldapBindPass` / `smtpPass` | AES-256-GCM v2; приложение их не расшифровывает (только запись) |

### Почему токен и пароль RC нельзя хешировать

Хеш годится только для того, что приложение **проверяет** (пароли пользователей, токены приглашений).
Токен и пароль Rocket.Chat приложение **предъявляет** серверу Rocket.Chat: токен — в каждом запросе
(`X-Auth-Token`), пароль — при автоматическом повторном входе, когда сессия RC истекла. Для этого нужно
исходное значение, поэтому возможно только обратимое шифрование.

Пароль хранится, чтобы рассылка не останавливалась при истечении сессии RC: при ответе 401 для подключения
«логин/пароль» без 2FA приложение один раз входит заново (`lib/rc-session-refresh.ts`), сохраняет новый
токен и повторяет запрос. Ограничения: не чаще 1 попытки на подключение за 30 минут (общая для реплик
отметка `SystemSetting rc-relogin:<id>`), никогда — для 2FA и личных токенов. Если сменить адрес сервера или
логин без ввода нового пароля, сохранённый пароль удаляется (чтобы он не ушёл на новый адрес).

**Рекомендуем личный токен** (Rocket.Chat → «Мой аккаунт» → «Токены для личного доступа»): пароль тогда
не нужен и не хранится, а токен можно отозвать в Rocket.Chat в любой момент.

## Слои защиты

1. **Шифрование v2** (`lib/encryption.ts`): AES-256-GCM, 12-байтный случайный IV, тег 16 байт.
   Формат `enc2:<kid>:<b|u>:<iv>:<tag>:<ct>`.
2. **Отдельный ключ на назначение**: из мастер-ключа через HKDF-SHA256 выводятся разные подключи для
   `rc-auth-token`, `rc-password`, `workspace-settings-secret`. Шифртекст одного назначения нельзя
   расшифровать как другое.
3. **Привязка к владельцу (AAD)**: токен и пароль RC зашифрованы с контекстом `ws:<userId владельца>`,
   секреты LDAP/SMTP — `wss:<workspaceId>`. Скопированный в чужую строку БД шифртекст не расшифруется.
4. **Ключ только в окружении**: `ENCRYPTION_KEY` (мастер-ключ = scrypt от него). Без ключа в production
   приложение не стартует. В БД и в репозитории ключа нет; `kid` (8 hex от sha256 подключа) ключ не раскрывает.
5. **Ни одного секрета в ответах API**: все запросы к `WorkspaceConnection` в API используют явный `select`;
   `authToken`/`encryptedPassword` не отдаются никогда, LDAP/SMTP — только маска `********` и флаг
   `ldapBindPassSet`/`smtpPassSet`. RC User ID отдаётся только владельцу подключения (нужен в форме редактирования).
6. **Ни одного секрета в логах**: `lib/sensitive-data.ts` (`redactString`, `redactForLog`, `safeErrorForLog`);
   в процессе приложения весь вывод `console.*` проходит через редактирование (`instrumentation.ts`):
   пароли, токены, `X-Auth-Token`, `Authorization`, cookie, коды 2FA, шифртексты заменяются на `[REDACTED]`.
   То же для `SecurityEvent.details` и `/api/errors/log`.
7. **Лимиты попыток подключения** (`lib/security.ts`): 10 проверок кредов RC за 15 минут на пользователя
   (in-memory + неудачи в БД) и 30 — с IP. Ответ при отказе входа одинаковый (не раскрывает, существует ли
   учётка). Пароль не фильтруется «подозрительными» шаблонами, формат кредов проверяется zod (`lib/credentials.ts`).
8. **Клиент**: поля паролей без автозаполнения сохранёнными паролями (`autoComplete="new-password"`),
   автозамены и проверки орфографии; пароль/токен/код 2FA стираются из состояния после отправки и при
   закрытии диалога; креды не попадают в URL, localStorage/sessionStorage и консоль.

## Ротация ключа

1. Сгенерировать новый ключ: `openssl rand -base64 32`.
2. `ENCRYPTION_KEY=<новый>`, `ENCRYPTION_KEY_PREVIOUS=<старый>` (несколько — через запятую). Перезапустить.
3. При старте контейнера `scripts/reencrypt-secrets.ts` перешифрует всё новым ключом (или вручную:
   `npx tsx scripts/reencrypt-secrets.ts --dry-run`, затем без `--dry-run`). Скрипт идемпотентный,
   печатает только счётчики; проверяет обратную расшифровку до записи; не затирает параллельные изменения.
4. Убедиться, что `undecryptable=0`, и убрать старый ключ из `ENCRYPTION_KEY_PREVIOUS`.

Отключить автоматический запуск при старте: `AUTO_REENCRYPT_SECRETS=false`. Ошибка скрипта не мешает запуску.

## Рекомендации по эксплуатации

- Закрыть доступ к PostgreSQL из сети: только контейнер приложения; отдельный пользователь БД с минимумом прав.
- Хранить `ENCRYPTION_KEY` вне репозитория и не на сервере БД; резервную копию ключа — отдельно от бэкапов БД.
- Шифровать бэкапы БД «на диске» и ограничить доступ к ним.
- Не использовать один и тот же секрет для `ENCRYPTION_KEY` и `JWT_SECRET`.
- При подозрении на утечку: отозвать токены RC (в Rocket.Chat — «Токены для личного доступа» / выход из всех
  сессий), сменить пароли RC подключений по логину/паролю, сменить `ENCRYPTION_KEY` по процедуре ротации.
- Предпочитать личные токены паролям; включать 2FA в Rocket.Chat (для таких подключений пароль не
  используется для повторного входа).

## Остаточные риски

- Тот, у кого есть **одновременно** дамп БД и `ENCRYPTION_KEY` (или доступ к работающему процессу),
  может расшифровать токены и пароли RC. Обратимое шифрование не защищает от компрометации сервера приложения.
- Пароль RC — это часто пароль LDAP (корпоративная учётка), поэтому его компрометация шире, чем
  компрометация токена. Поэтому рекомендуется личный токен.
- Строки JS нельзя гарантированно затереть в памяти; расшифрованный пароль живёт в памяти процесса
  только во время повторного входа.
- In-memory лимиты считаются на процесс; для нескольких реплик общий лимит — по неудачам в БД и nginx `limit_req`.
- Записи, зашифрованные неизвестным ключом, расшифровать нельзя — такие подключения нужно переподключить
  (скрипт перешифровки выводит их id).
